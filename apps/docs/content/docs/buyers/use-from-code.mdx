The Gyblos [desktop app](/en/buyers/desktop-app) runs a small server on your computer that speaks the
OpenAI and Anthropic APIs. Coding agents and programs written for those APIs use Gyblos models when you
give them the app's **Base URL** and an **API key**. You don't install anything else.

Your prompt reaches the seller that answers it. That seller's machine runs the model and can read your
prompt. Don't send passwords, keys or other secrets. See [Data and privacy](/en/reference/data-and-privacy).

## Automatic seller selection

Auto lets your buyer pick a seller for you. By default it uses free offers only. To let it use paid offers, open
**Usage & payments → Limits** in the desktop app and choose **Manage chat budget**. Under **Automatic seller
selection**, check **Allow paid offers in Auto**, then enter:

- the maximum per response, in USDC;
- the maximum input price and the maximum output price, in USDC per million tokens.

Then choose **Save Auto settings**. The section appears when your buyer finds sellers on its own (open
discovery), and you can save it only for the buyer the app manages: for a buyer you connected separately, the app refuses the change. In chat, open the model and select **Auto**. For now, paid Auto in chat covers `qwen3-0.6b` only;
for other models Auto still uses free offers only, though you can still pick a specific paid seller from the model menu.

These limits apply to chat and to every API key on this buyer, so your coding tools follow them too. The maximum
per response is the buyer's limit for every paid answer, not only Auto's, and it stays when you turn paid offers
off. Auto asks verified sellers for signed offers. The remaining budget of each API key still applies, and a key
with a limit of `0` can only use free offers. Auto may settle the previous channel before opening a replacement
within the remaining deposit authority. To return Auto to free offers only, clear **Allow paid offers in Auto**
and choose **Save Auto settings**.

## Prerequisites [#before-you-start]

- The [Gyblos desktop app](/en/buyers/desktop-app), installed and open. Keep it open while your tools use
  it.
- For priced models: a budget authorized in the app's **Payments**. Free models need no wallet.

## Create an API key [#create-an-api-key]

1. In the app, open **Connections**. If it asks you to connect your buyer, choose **Open Usage & payments** and
   start it there.
2. Choose **Create your first API key** or **New API key**, enter a **Name** and a **Limit for this key**, then choose **Create API key**.
   The limit is the total this key may spend, in devnet USDC. It never resets and can't be raised later.
   A limit of `0` allows free models only.
3. Choose **Copy API key** and **Copy Base URL**. The app keeps the key hidden on screen; paste it
   straight into your tool.

You can copy a key only in the app session that created it. After a restart, a tool that already has the
key keeps working, but the app can't copy the key again. The key never appears in saved agent
configuration or in chat history. **Revoke key** stops new requests with that key; what it already spent
stays recorded.

The app-managed buyer keeps its Base URL across restarts. A separately connected buyer may use a different URL. After a restart, choose **Copy Base URL** again and, if
it changed, update your tool or choose **Write configuration** again.

## Connect a coding agent [#connect-a-coding-agent]

The app sets up OpenCode, pi, Codex CLI and Claude Code for you, with every model it can use:

1. In **Connections**, open **Details** for an active key and choose **Connect a tool**.
2. Pick the **Tool** and review the configuration the app shows.
3. Choose **Write configuration**. The app changes only the `gyblos` provider and keeps a copy of the
   previous file. For Claude Code, copy the variables into your shell instead.
4. The configuration reads the key from `GYBLOS_API_KEY`. Set it in the shell that starts the agent:

```sh
export GYBLOS_API_KEY=YOUR_API_KEY
```

Replace `YOUR_API_KEY` with the key you copied.

When the app can't learn a model's context size, the configuration uses 32,768 tokens of context, and the
output limit is the buyer's answer limit. The buyer shortens the answer limit to fit the seller it picks.
When the conversation does not fit, your tool gets a standard "context too long" error and compacts the
conversation instead of stopping.
When the models change, choose **Write configuration** again.

Then pick a Gyblos model with `/models` (OpenCode), `/model` (pi and Claude Code) or
`codex --profile gyblos`. Agents that send many tools and long instructions, such as Claude Code, need a
seller that serves a larger model.

## Use the key in your own code [#use-the-key]

In the commands below, set `BASE_URL` to the Base URL you copied and `GYBLOS_API_KEY` to your key. First
list the models you can use:

```sh
curl "$BASE_URL/models" -H "Authorization: Bearer $GYBLOS_API_KEY"
```

Use one of the listed `id` values as `model`. Listing models doesn't spend from the key's limit.

### OpenAI SDK [#openai-sdk]

Use the Base URL as it is:

```js
import OpenAI from 'openai';

const client = new OpenAI({
  baseURL: process.env.BASE_URL,
  apiKey: process.env.GYBLOS_API_KEY,
  maxRetries: 0,
});
const stream = await client.chat.completions.create({
  model: 'qwen3-0.6b',
  stream: true,
  messages: [
    { role: 'system', content: 'Be brief.' },
    { role: 'user', content: 'My dog is called Rocky.' },
    { role: 'assistant', content: 'Got it: your dog is Rocky.' },
    { role: 'user', content: "What is my dog's name?" },
  ],
});
for await (const chunk of stream)
  process.stdout.write(chunk.choices[0]?.delta?.content ?? '');
```

### Anthropic SDK [#anthropic-sdk]

Use the Base URL without its final `/v1`. As with Anthropic, `max_tokens` is required:

```js
import Anthropic from '@anthropic-ai/sdk';

const client = new Anthropic({
  baseURL: process.env.BASE_URL.replace(/\/v1$/, ''),
  apiKey: process.env.GYBLOS_API_KEY,
  maxRetries: 0,
});
const message = await client.messages.create({
  model: 'qwen3-0.6b',
  max_tokens: 200,
  system: 'Be brief.',
  messages: [
    { role: 'user', content: 'My dog is called Rocky.' },
    { role: 'assistant', content: 'Got it: your dog is Rocky.' },
    { role: 'user', content: "What is my dog's name?" },
  ],
});
console.log(message.content[0].text);
```

## What works [#what-works-today]

| Feature                                                              | Status                                   |
| -------------------------------------------------------------------- | ---------------------------------------- |
| Whole conversations: system message, history, new message            | Yes, up to 1024 messages                 |
| OpenAI `POST /v1/chat/completions` and Anthropic `POST /v1/messages` | Yes, whole answers and streaming         |
| OpenAI `POST /v1/responses` (Codex CLI)                              | Yes, whole answers and streaming         |
| `GET /v1/models`                                                     | Yes, every model the app can use         |
| Free offers                                                          | Yes                                      |
| Priced offers (devnet USDC)                                          | Yes, within the key's spend limit        |
| Tools (function calling), both formats, whole answers and streaming  | Yes, on free offers; see [Tools](#tools) |
| Cursor agent mode                                                    | No: it calls from Cursor's cloud         |
| Images, structured output, several answers per request               | No: refused with a 400 error             |

By default, a seller serves each buyer up to **30 answers per minute**. An answer is at most **4096
tokens**; a longer answer stops at the limit with finish reason `length`.

The Responses API refuses `parallel_tool_calls: false`, non-default sampling and non-neutral reasoning
before it contacts a seller, because the signed request can't carry those constraints. Codex versions
that require them don't work. In every client, turn off HTTP and stream retries.

## Tools [#tools]

Send `tools` as each API defines them. When the model wants a tool, the answer ends with
`finish_reason: "tool_calls"` (Anthropic: `stop_reason: "tool_use"`) and carries the call. Your program
runs the tool and sends the result back in the next request, with the whole conversation. A tool description
longer than 8 KiB is shortened to fit. More than 128 tools gets an error for the whole list; a name that is not 1
to 64 letters, digits, `_` or `-`, a repeated name, or a schema over 64 KiB gets an error naming the tool, such as
`tools[3]: ...`. In the Chat Completions and Messages formats, prompt-cache marks and reasoning fields from other
providers in the history are ignored:

```js
import OpenAI from 'openai';

const client = new OpenAI({
  baseURL: process.env.BASE_URL,
  apiKey: process.env.GYBLOS_API_KEY,
  maxRetries: 0,
});
const tools = [
  {
    type: 'function',
    function: {
      name: 'get_time',
      description: 'Current local time in a city',
      parameters: {
        type: 'object',
        properties: { city: { type: 'string' } },
        required: ['city'],
      },
    },
  },
];
const messages = [
  { role: 'user', content: 'What time is it in Santiago? Use the tool.' },
];
const first = await client.chat.completions.create({
  model: 'qwen3-0.6b',
  messages,
  tools,
});
const call = first.choices[0].message.tool_calls[0];
// Run the tool yourself, then send its result back.
messages.push(first.choices[0].message, {
  role: 'tool',
  tool_call_id: call.id,
  content: '15:42',
});
const second = await client.chat.completions.create({
  model: 'qwen3-0.6b',
  messages,
  tools,
});
console.log(second.choices[0].message.content);
```

With the Anthropic SDK, send `tools` with `input_schema`, read the `tool_use` blocks and answer with
`tool_result` blocks, as with Anthropic. Gyblos asks only sellers that serve tools; if none does, it
answers 503 and says so. Tools work on free offers only.

## Switch models [#switch-models]

Send another name as `model` (`/model` in most agents). Each request carries the whole conversation, so
the next model reads everything said before. The first answer after a switch can take longer, because
the new seller has nothing cached. A name the app can't use gets a 404 that lists the names it can.

## If a seller drops [#if-a-seller-drops]

What happens when a seller fails depends on how far the answer got:

| When the seller fails                                                       | What happens                                                                                             |
| --------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------- |
| Before any text reached your tool                                           | Gyblos sends the request to another seller of the same model, at most three in total, within 180 seconds |
| After text reached your tool                                                | The request ends with an error; the answer is not restarted elsewhere                                    |
| The seller itself answers with an error (busy, daily limit, engine failure) | The request ends with that error                                                                         |

A broken connection may deliver no response headers at all, so turn off HTTP and stream retries in your
tool. Resending a request yourself starts a new seller selection.

Some sellers run on slow hardware. Each seller measures how fast it reads prompts, and your buyer tells
every seller it asks roughly how big a request is before choosing one: only the size, rounded up to a
multiple of 1024 tokens, never the text. A seller that would not read a long prompt, such as a coding
agent's, in time declines, and your buyer picks another seller without sending it the prompt. If every
seller asked declined for that reason, the error says so; shorten the conversation (Codex and OpenCode
can compact it) or try again later.

A seller that has not measured itself yet can still time out. Then the request ends with `reason`
`engine_timeout` and a message that the seller was too slow for a request this size. Send it again. Each
seller learns its speed from the answers it gives, so this becomes rarer as sellers measure themselves.

## Options and errors [#options-and-errors]

| Option                                                                                          | Behavior                                                                               |
| ----------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------- |
| `temperature`, `top_p`, `user`, `metadata`, `stream_options`; Anthropic `thinking` (always off) | Accepted and ignored                                                                   |
| `response_format`, `n`, `logprobs`                                                              | Refused unless neutral: `text`, `1`, `false`                                           |
| `stop` (up to 4 strings) and Anthropic `stop_sequences`                                         | Honored on your computer                                                               |
| Images                                                                                          | Refused by Chat Completions and Anthropic; replaced by a text placeholder in Responses |

Gyblos applies stop sequences on your computer: the answer ends just before the first sequence, with
finish reason `stop` (Anthropic: `stop_reason: "stop_sequence"`). A cut answer carries no tool calls. The
seller doesn't receive the sequences and keeps generating, so a stream closes only when the seller
finishes, and `usage` counts everything it generated.

| Answer                        | Meaning                                                                                     |
| ----------------------------- | ------------------------------------------------------------------------------------------- |
| 400                           | The request uses something Gyblos doesn't support; the message and `param` name it          |
| 400 `BUYER_KEY_LIMIT_REACHED` | The key's remaining limit can't cover this request; nothing was sent. Create a new key      |
| 403 `BUYER_KEY_REVOKED`       | The key was revoked; nothing was sent                                                       |
| 404                           | The app can't use that model; the message lists the ones it can                             |
| 503                           | No seller is available. `Retry-After` suggests when to try again; retrying is your decision |
| 503 `BUYER_KEY_NEEDS_REVIEW`  | An earlier paid request on this key has an uncertain outcome. Review it in **Payments**     |
| 504                           | The seller didn't answer in time                                                            |

If the buyer confirms a cancellation before payment preparation and dispatch, the reserved allowance becomes available again.

Errors use each API's own shape, so SDKs raise their usual exceptions. For other problems, see
[Troubleshooting](/en/help/troubleshooting#buyer-and-desktop).

## Clients made for OpenRouter [#clients-made-for-openrouter]

OpenRouter uses the same Chat Completions format, plus a few fields of its own. A client or agent set up
for OpenRouter works when you set its base URL to the app's Base URL and its API key to your Gyblos key:

- `provider`, `route`, `transforms`, `usage`, `debug`, `reasoning`, `verbosity`, `prediction` and the
  sampling fields `top_k`, `min_p`, `top_a` and `repetition_penalty` are accepted and ignored. They choose
  among OpenRouter's providers or tune sampling, and don't change what a seller is asked.
- `models`, a fallback list of up to 8 names, is honored: the answer comes from the first name, `model`
  first, that the app can use, and the reply's `model` says which. If it can use none, the 404 lists the
  names it can.
- OpenRouter-style names find the same model: `qwen/qwen3-0.6b` and `qwen/qwen3-0.6b:free` answer as
  `qwen3-0.6b`. The suffixes `:free`, `:nitro` and `:floor` only choose a provider on OpenRouter. A
  suffix that changes the answer, such as `:online` (web search), doesn't match the plain model.
- `plugins` (for example web search) and `web_search_options` are refused with a 400 rather than skipped,
  so a client never shows an answer as searched when it wasn't.
