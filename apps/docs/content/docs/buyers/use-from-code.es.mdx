title: Conecta tus herramientas de código
description: Crea una API key en la app de Gyblos y usa modelos de Gyblos desde agentes de código, los SDK de OpenAI y Anthropic y clientes de OpenRouter.
---

La [app de escritorio](/es/buyers/desktop-app) de Gyblos ejecuta un pequeño servidor en tu equipo que
habla las API de OpenAI y Anthropic. Los agentes de código y los programas escritos para esas API usan
modelos de Gyblos cuando les das la **Base URL** de la app y una **API key**. No instalas nada más.

Tu prompt llega al vendedor que lo responde. La máquina de ese vendedor ejecuta el modelo y puede leer tu
prompt. No envíes contraseñas, llaves ni otros secretos. Consulta
[Datos y privacidad](/es/reference/data-and-privacy).

Si se corta una respuesta pagada, conserva el texto parcial y envía una pregunta nueva. Con la renovación autorizada, el comprador comprueba el cargo y el reembolso y puede abrir un reemplazo con el mismo vendedor. Mientras el pago siga pendiente de confirmación, las peticiones pagadas siguen bloqueadas.

Si tu herramienta reintenta la pregunta interrumpida con la misma API key, la selección automática también bloquea ese reintento cuando encuentra un vendedor gratuito. Envía una pregunta nueva para continuar. En Desktop puedes elegir Gratis explícitamente para volver a hacer la pregunta original.

## Selección automática de vendedor

Auto deja que tu comprador elija un vendedor por ti. Por defecto usa solo ofertas gratis. Para que use ofertas
pagadas, abre **Usage & payments → Limits** en la app de escritorio y elige **Manage chat budget**. En
**Automatic seller selection**, marca **Allow paid offers in Auto** y escribe:

- el máximo por respuesta, en USDC;
- el precio máximo de entrada y el precio máximo de salida, en USDC por millón de tokens.

Luego elige **Save Auto settings**. La sección aparece cuando tu comprador busca vendedores por su cuenta
(descubrimiento abierto), y solo se puede guardar para el comprador que maneja la app: para un comprador que conectaste por separado, la app rechaza el cambio. En el chat, abre el modelo y elige **Auto**. Por ahora, Auto pagado
en el chat cubre solo `qwen3-0.6b`; para los demás modelos Auto sigue usando solo ofertas gratis, aunque igual puedes elegir un vendedor pagado específico en el menú del modelo.
Al elegir Auto en Chat, la aplicación compara los precios de entrada y salida anunciados con tus límites guardados antes de contar los fondos del canal de un vendedor. Si el catálogo está incompleto, Chat consulta más ofertas de ese modelo. Puedes volver a intentarlo con el mismo borrador si aún no puede verificar un vendedor dentro de tus límites.
Si falla una página posterior, la aplicación puede emitir un código de diagnóstico local sin incluir el modelo, el vendedor ni los detalles de la búsqueda.

Estos límites se aplican al chat y a todas las claves API de este comprador, así que tus herramientas de código
también los respetan. El máximo por respuesta es el límite del comprador para toda respuesta pagada, no solo
para Auto, y se mantiene cuando desactivas las ofertas pagadas. Auto pide ofertas firmadas a vendedores
verificados. Se sigue respetando el saldo de cada clave API, y una clave con límite `0` solo puede usar ofertas
gratis. Antes de activar, cambiar o desactivar la renovación, deja que terminen las peticiones del comprador administrado por la app y abre **Usage & payments → Limits**. Si tienes un presupuesto activo de Chat de pago, elige **Manage chat budget → Finish session**. Para activar la renovación, elige **Set budget**. Ingresa el presupuesto total y elige **Authorize renewal**. En **Manage budget** puedes cambiarlo o elegir **Turn off renewal**. Al desactivarlo, las herramientas pueden seguir usando el saldo del canal ya financiado. Con la renovación activada, OpenCode y tus clientes API pueden seguir con el mismo vendedor cuando el canal se queda sin saldo para la próxima respuesta. El comprador verifica la liquidación y abre un solo reemplazo dentro del límite por depósito, el presupuesto total compartido y el límite de la clave. Las tarifas por token pueden cambiar dentro de los máximos de entrada y salida que aprobaste. Si no alcanza el presupuesto o el pago requiere revisión, la herramienta recibe un error. Con la política de canal predeterminada, un cambio de vendedor en Auto autorizado por el titular puede liquidar el canal anterior y usar el depósito autorizado restante. Para que
Auto vuelva a usar solo ofertas gratis, desmarca **Allow paid offers in Auto** y elige **Save Auto settings**.

## Requisitos previos [#antes-de-empezar]

- La [app de escritorio de Gyblos](/es/buyers/desktop-app), instalada y abierta. Mantenla abierta mientras
  tus herramientas la usan.
- Para modelos con precio: un presupuesto autorizado en **Payments** dentro de la app. Los modelos gratis
  no necesitan billetera.

## Crea una API key [#crear-una-api-key]

1. En la app, abre **Connections**. Si te pide conectar tu comprador, elige **Open Usage & payments** y
   arráncalo ahí.
2. Elige **Create your first API key** o **New API key**, escribe un **Name** y un **Limit for this key**, y elige **Create API key**. El
   límite es el total que puede gastar esta key, en USDC de devnet. Nunca se reinicia y no se puede
   subir después. Un límite de `0` permite solo modelos gratis.
3. Elige **Copy API key** y **Copy Base URL**. La app mantiene la key oculta en pantalla; pégala
   directamente en tu herramienta.

Solo puedes copiar una key en la sesión de la app que la creó. Después de reiniciar, una herramienta que
ya tiene la key sigue funcionando, pero la app no puede volver a copiarla. La key nunca
aparece en la configuración guardada del agente ni en el historial del chat. **Revoke key** detiene las
solicitudes nuevas con esa key; lo que ya gastó queda registrado.

El comprador gestionado por la app conserva su Base URL al reiniciar. Un comprador conectado por separado puede usar otra URL. Después de reiniciar, elige otra vez **Copy Base URL**
y, si cambió, actualiza tu herramienta o elige otra vez **Write configuration**.

## Conecta un agente de código [#conectar-un-agente-de-codigo]

La app configura OpenCode, pi, Codex CLI y Claude Code por ti, con todos los modelos que puede usar:

1. En **Connections**, abre **Details** de una key activa y elige **Connect a tool**.
2. Elige la **Tool** y revisa la configuración que muestra la app.
3. Elige **Write configuration**. La app cambia solo el proveedor `gyblos` y guarda una copia del archivo
   anterior. Para Claude Code, copia las variables en tu shell.
4. La configuración lee la key desde `GYBLOS_API_KEY`. Defínela en la shell que arranca el agente:

```sh
export GYBLOS_API_KEY=YOUR_API_KEY
```

Reemplaza `YOUR_API_KEY` por la key que copiaste.

Cuando la app no puede saber el tamaño de contexto de un modelo, la configuración usa 32.768 tokens de
contexto, y el límite de salida es el límite de respuesta del comprador. El comprador acorta el límite de
respuesta para que quepa en el vendedor que elige. Si la conversación no cabe, tu herramienta recibe un
error estándar de "contexto demasiado largo" y compacta la conversación en vez de detenerse. Cuando cambien los modelos, elige **Write
configuration** otra vez.

Luego elige un modelo de Gyblos con `/models` (OpenCode), `/model` (pi y Claude Code) o
`codex --profile gyblos`. Los agentes que envían muchas herramientas e instrucciones largas, como Claude
Code, necesitan un vendedor que sirva un modelo más grande.

## Usa la key en tu propio código [#usar-la-key]

En los comandos de abajo, define `BASE_URL` con la Base URL que copiaste y `GYBLOS_API_KEY` con tu key.
Primero lista los modelos que puedes usar:

```sh
curl "$BASE_URL/models" -H "Authorization: Bearer $GYBLOS_API_KEY"
```

Usa uno de los `id` de la lista como `model`. Listar modelos no gasta del límite de la key.

### SDK de OpenAI [#sdk-de-openai]

Usa la Base URL tal cual:

```js
import OpenAI from 'openai';

const client = new OpenAI({
  baseURL: process.env.BASE_URL,
  apiKey: process.env.GYBLOS_API_KEY,
  maxRetries: 0,
});
const stream = await client.chat.completions.create({
  model: 'qwen3-0.6b',
  stream: true,
  messages: [
    { role: 'system', content: 'Be brief.' },
    { role: 'user', content: 'My dog is called Rocky.' },
    { role: 'assistant', content: 'Got it: your dog is Rocky.' },
    { role: 'user', content: "What is my dog's name?" },
  ],
});
for await (const chunk of stream)
  process.stdout.write(chunk.choices[0]?.delta?.content ?? '');
```

### SDK de Anthropic [#sdk-de-anthropic]

Usa la Base URL sin el `/v1` final. Igual que con Anthropic, `max_tokens` es obligatorio:

```js
import Anthropic from '@anthropic-ai/sdk';

const client = new Anthropic({
  baseURL: process.env.BASE_URL.replace(/\/v1$/, ''),
  apiKey: process.env.GYBLOS_API_KEY,
  maxRetries: 0,
});
const message = await client.messages.create({
  model: 'qwen3-0.6b',
  max_tokens: 200,
  system: 'Be brief.',
  messages: [
    { role: 'user', content: 'My dog is called Rocky.' },
    { role: 'assistant', content: 'Got it: your dog is Rocky.' },
    { role: 'user', content: "What is my dog's name?" },
  ],
});
console.log(message.content[0].text);
```

## Qué funciona [#que-funciona-hoy]

| Función                                                                   | Estado                                                        |
| ------------------------------------------------------------------------- | ------------------------------------------------------------- |
| Conversaciones completas: mensaje de sistema, historial y mensaje nuevo   | Sí, hasta 1024 mensajes                                       |
| OpenAI `POST /v1/chat/completions` y Anthropic `POST /v1/messages`        | Sí, respuestas completas y streaming                          |
| OpenAI `POST /v1/responses` (Codex CLI)                                   | Sí, respuestas completas y streaming                          |
| `GET /v1/models`                                                          | Sí, todos los modelos que la app puede usar                   |
| Ofertas gratis                                                            | Sí                                                            |
| Ofertas con precio (USDC de devnet)                                       | Sí, dentro del límite de gasto de la key                      |
| Herramientas (function calling), ambos formatos, completas y en streaming | Sí, en ofertas gratis; consulta [Herramientas](#herramientas) |
| Modo agente de Cursor                                                     | No: llama desde la nube de Cursor                             |
| Imágenes, salida estructurada, varias respuestas por solicitud            | No: se rechazan con un error 400                              |

Por defecto, un vendedor atiende a cada comprador hasta **30 respuestas por minuto**. Una respuesta tiene
como máximo **4096 tokens**; una respuesta más larga se corta en el límite con finish reason `length`.

La API Responses rechaza `parallel_tool_calls: false`, el muestreo distinto del predeterminado y el
razonamiento no neutro antes de contactar a un vendedor, porque la solicitud firmada no puede llevar esas
restricciones. Las versiones de Codex que las exigen no funcionan. En todos los clientes, desactiva los
reintentos HTTP y de stream.

## Herramientas [#herramientas]

Envía `tools` como define cada API. Cuando el modelo quiere usar una herramienta, la respuesta termina con
`finish_reason: "tool_calls"` (Anthropic: `stop_reason: "tool_use"`) y trae la llamada. Tu programa
ejecuta la herramienta y devuelve el resultado en la siguiente solicitud, con toda la conversación. Una
descripción de herramienta de más de 8 KiB se acorta para que quepa. Más de 128 herramientas reciben un error para
toda la lista; un nombre que no tenga de 1 a 64 letras, dígitos, `_` o `-`, un nombre repetido o un esquema de más
de 64 KiB reciben un error que nombra la herramienta, como `tools[3]: ...`. En los formatos Chat Completions y
Messages, las marcas de caché y los campos de razonamiento de otros proveedores en el historial se ignoran:

```js
import OpenAI from 'openai';

const client = new OpenAI({
  baseURL: process.env.BASE_URL,
  apiKey: process.env.GYBLOS_API_KEY,
  maxRetries: 0,
});
const tools = [
  {
    type: 'function',
    function: {
      name: 'get_time',
      description: 'Current local time in a city',
      parameters: {
        type: 'object',
        properties: { city: { type: 'string' } },
        required: ['city'],
      },
    },
  },
];
const messages = [
  { role: 'user', content: 'What time is it in Santiago? Use the tool.' },
];
const first = await client.chat.completions.create({
  model: 'qwen3-0.6b',
  messages,
  tools,
});
const call = first.choices[0].message.tool_calls[0];
// Run the tool yourself, then send its result back.
messages.push(first.choices[0].message, {
  role: 'tool',
  tool_call_id: call.id,
  content: '15:42',
});
const second = await client.chat.completions.create({
  model: 'qwen3-0.6b',
  messages,
  tools,
});
console.log(second.choices[0].message.content);
```

Con el SDK de Anthropic, envía `tools` con `input_schema`, lee los bloques `tool_use` y responde con
bloques `tool_result`, igual que con Anthropic. Gyblos solo pregunta a vendedores que sirven
herramientas; si ninguno lo hace, responde 503 y lo dice. Las herramientas funcionan solo en ofertas
gratis.

## Cambia de modelo [#cambiar-de-modelo]

Envía otro nombre en `model` (`/model` en la mayoría de los agentes). Cada solicitud lleva toda la
conversación, así que el siguiente modelo lee todo lo anterior. La primera respuesta después del cambio
puede tardar más, porque el nuevo vendedor no tiene nada en caché. Un nombre que la app no puede usar
recibe un 404 con la lista de los que sí puede.

## Si un vendedor se cae [#si-un-vendedor-se-cae]

Lo que pasa cuando un vendedor falla depende de cuánto avanzó la respuesta:

| Cuándo falla el vendedor                                                           | Qué pasa                                                                                                      |
| ---------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------- |
| Antes de que llegue texto a tu herramienta                                         | Gyblos envía la solicitud a otro vendedor del mismo modelo, como máximo tres en total, dentro de 180 segundos |
| Después de que llegó texto a tu herramienta                                        | La solicitud termina con un error; la respuesta no se reinicia en otro lado                                   |
| El propio vendedor responde con un error (ocupado, límite diario, falla del motor) | La solicitud termina con ese error                                                                            |

Cuando tu agente envía varias solicitudes juntas, el comprador puede admitir hasta cuatro a la vez. Cada solicitud espera un turno dentro de su plazo original. Al cancelar una solicitud en cola, se retira antes de contactar al vendedor. Una cola llena devuelve HTTP 429. Si el vendedor está renovando su catálogo, el comprador puede esperar la renovación dentro de la misma solicitud.

Con una clave de API, el reenvío automático tras un corte de conexión o al agotarse la espera local por la primera respuesta se limita a ofertas gratuitas verificadas y termina en cuanto tu herramienta recibe contenido. Un posible envío pagado termina los reintentos automáticos.

Una conexión cortada puede no entregar ninguna cabecera de respuesta, así que desactiva los reintentos
HTTP y de stream en tu herramienta. Si reenvías una solicitud tú mismo, empieza una nueva selección de
vendedor.

Algunos vendedores usan hardware lento. Cada vendedor mide qué tan rápido lee los prompts, y tu comprador
le dice a cada vendedor que consulta el tamaño aproximado de la solicitud antes de elegir: solo el tamaño,
redondeado hacia arriba a un múltiplo de 1024 tokens, nunca el texto. Un vendedor que no alcanzaría a leer
a tiempo un prompt largo, como el de un agente de código, lo rechaza, y tu comprador elige otro vendedor
sin enviarle el prompt. Si todos los vendedores consultados lo rechazaron por eso, el error lo dice; acorta
la conversación (Codex y OpenCode pueden compactarla) o vuelve a intentar más tarde.

Un vendedor que todavía no se ha medido puede quedarse sin tiempo. Entonces la solicitud termina con
`reason` `engine_timeout` y un mensaje que dice que el vendedor fue demasiado lento para una solicitud de
ese tamaño. Envíala de nuevo. Cada vendedor aprende su velocidad de las respuestas que da, así que esto pasa
cada vez menos a medida que los vendedores se miden.

## Opciones y errores [#opciones-y-errores]

| Opción                                                                                           | Comportamiento                                                                              |
| ------------------------------------------------------------------------------------------------ | ------------------------------------------------------------------------------------------- |
| `temperature`, `top_p`, `user`, `metadata`, `stream_options`; Anthropic `thinking` (siempre off) | Se aceptan y se ignoran                                                                     |
| `response_format`, `n`, `logprobs`                                                               | Se rechazan salvo que sean neutros: `text`, `1`, `false`                                    |
| `stop` (hasta 4 cadenas) y `stop_sequences` de Anthropic                                         | Se respetan en tu equipo                                                                    |
| Imágenes                                                                                         | Chat Completions y Anthropic las rechazan; Responses las reemplaza por un marcador de texto |

Gyblos aplica las secuencias de parada en tu equipo: la respuesta termina justo antes de la primera
secuencia, con finish reason `stop` (Anthropic: `stop_reason: "stop_sequence"`). Una respuesta cortada no
trae llamadas a herramientas. El vendedor no recibe las secuencias y sigue generando, así que un stream
se cierra solo cuando el vendedor termina, y `usage` cuenta todo lo que generó.

| Respuesta                                                                            | Significado                                                                                       |
| ------------------------------------------------------------------------------------ | ------------------------------------------------------------------------------------------------- |
| 400                                                                                  | La solicitud usa algo que Gyblos no admite; el mensaje y `param` lo nombran                       |
| 400 `BUYER_KEY_LIMIT_REACHED`                                                        | Lo que queda del límite de la key no cubre esta solicitud; no se envió nada. Crea una key nueva   |
| 403 `BUYER_KEY_REVOKED`                                                              | La key fue revocada; no se envió nada                                                             |
| 404                                                                                  | La app no puede usar ese modelo; el mensaje lista los que sí puede                                |
| 503                                                                                  | No hay vendedores disponibles. `Retry-After` sugiere cuándo reintentar; reintentar es tu decisión |
| 503 (Chat Completions, Anthropic Messages), 400 (Responses) `BUYER_KEY_NEEDS_REVIEW` | El registro de API keys requiere revisión. Consulta su estado en **Connections**.                 |
| 504                                                                                  | Venció el plazo en la cola local o el vendedor tardó demasiado                                    |

Si el plazo vence en la cola local, el error 504 incluye `gyblos_never_sent: true`. Puedes reintentar con seguridad.

La tabla indica el estado HTTP antes de enviar las cabeceras de respuesta. Cuando el registro requiere revisión, el comprador envía `x-should-retry: false`. Configura el cliente para detener los reintentos automáticos mientras dure la revisión. En el cuerpo JSON de un rechazo por revisión de claves en Responses, el código de Gyblos aparece en `error.code` si se verificó que la solicitud no se envió, o en `error.gyblos_code` si pudo haberse enviado.

Una vez iniciado el stream, el estado HTTP sigue siendo 200. Chat Completions envía un último evento de datos con `error.code`. Anthropic Messages envía un evento `error` con `error.code`. Responses envía un evento `response.failed` con `response.error.gyblos_code`.

Los errores usan la forma de cada API, así que los SDK lanzan sus excepciones habituales. Para otros
problemas, consulta [Solución de problemas](/es/help/troubleshooting#escritorio-y-comprador-local).

Si el comprador confirma la cancelación antes de preparar el pago y enviar la solicitud, el importe reservado vuelve a estar disponible.

## Clientes hechos para OpenRouter [#clientes-hechos-para-openrouter]

OpenRouter usa el mismo formato Chat Completions, más algunos campos propios. Un cliente o agente
configurado para OpenRouter funciona cuando pones como URL base la Base URL de la app y como API key tu
key de Gyblos:

- `provider`, `route`, `transforms`, `usage`, `debug`, `reasoning`, `verbosity`, `prediction` y los
  campos de muestreo `top_k`, `min_p`, `top_a` y `repetition_penalty` se aceptan y se ignoran. Eligen
  entre los proveedores de OpenRouter o ajustan el muestreo, y no cambian lo que se le pide a un vendedor.
- `models`, una lista de respaldo de hasta 8 nombres, se respeta: la respuesta sale del primer nombre,
  empezando por `model`, que la app puede usar, y el `model` de la respuesta dice cuál. Si no puede usar
  ninguno, el 404 lista los nombres que sí puede.
- Los nombres al estilo OpenRouter encuentran el mismo modelo: `qwen/qwen3-0.6b` y `qwen/qwen3-0.6b:free`
  responden como `qwen3-0.6b`. Los sufijos `:free`, `:nitro` y `:floor` solo eligen un proveedor en
  OpenRouter. Un sufijo que cambia la respuesta, como `:online` (búsqueda web), no coincide con el modelo
  simple.
- `plugins` (por ejemplo búsqueda web) y `web_search_options` se rechazan con un 400 en vez de omitirse,
  para que un cliente nunca muestre una respuesta como buscada cuando no lo fue.
