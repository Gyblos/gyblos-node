---
title: Identity and backups
description: Know your seller's keys, where its data lives, how to back up the keys and what is safe to share for support.
---

Your seller's identity is its keys. If you lose them, the seller gets a new NodeId that your used invite code
cannot register, and nobody can reach the USDC on the old owner address. The installer creates the keys
once; rerunning it or updating keeps them. `gyblos seller init` writes configuration only and never creates
or recovers keys.

## The seller keys [#keys]

A seller has four private keys: one network key and three Solana keypairs.

| Key        | File               | What it does                                                                       |
| ---------- | ------------------ | ---------------------------------------------------------------------------------- |
| Node key   | `node.key`         | The seller's network identity, its public **NodeId**. Buyers connect to it.        |
| Owner      | `owner.json`       | Enrolled in the 8004 agent registry, pays registration and **receives your USDC**. |
| Authorizer | `authorizer.json`  | Signs the seller's payment permissions. Holds no funds.                            |
| Fee payer  | `facilitator.json` | Pays the Solana fees and rent of your payment transactions. Holds devnet SOL.      |

`gyblos doctor` prints the public NodeId and the owner and fee payer addresses. Those are safe to share. The
files are private keys: never share or upload them.

## Where your data lives [#what-lives-where]

| Install type          | Configuration (`config.toml`, `seller.env`) | Keys and seller state                    |
| --------------------- | ------------------------------------------- | ---------------------------------------- |
| Docker seller         | `~/gyblos-seller/`                          | Docker volume, at `/data/seller/` inside |
| Native seller         | `~/.gyblos/`                                | `~/.gyblos/seller/`                      |
| Windows native seller | `%USERPROFILE%\.gyblos\`                    | `%USERPROFILE%\.gyblos\seller\`          |

- `config.toml` holds models, limits and publication. Review it before sharing: custom URLs can contain
  credentials.
- `seller.env` holds provider API keys and other private variables. Never upload or display it.
- The seller state holds the keys, private registration attempts, the public sequence, payment records,
  receipts and the tokenizer. Never upload it or any of its files.
- A Docker seller also has `compose.yaml` and a separate Ollama volume with the downloaded model.

A Docker seller's volume names come from the Compose project, which is the folder name. Moving or renaming
the folder, or changing the project name, makes the seller look newly installed. Never move it or prune its
volumes as a troubleshooting step.

## Keep your identity when you stop [#preserve-identity-when-stopping]

Stop a Docker seller with `docker compose stop seller`. `docker compose down` also keeps the volumes, but
`docker compose down -v` deletes them with the keys. On a native seller,
`gyblos seller service uninstall` stops the seller and keeps its files.

## Back up the keys [#back-up-keys]

Copy the four key files once, after installing; they never change. At minimum, keep `owner.json` (your USDC
and registry enrollment) and `node.key` (the NodeId your invite registered).

For a Docker seller, run from `~/gyblos-seller`:

```bash
mkdir -p ~/gyblos-keys-backup && chmod 700 ~/gyblos-keys-backup
for key in node.key owner.json authorizer.json facilitator.json; do
  docker compose cp "seller:/data/seller/$key" ~/gyblos-keys-backup/
done
```

For a native seller on macOS or Linux:

```bash
mkdir -p ~/gyblos-keys-backup && chmod 700 ~/gyblos-keys-backup
for key in node.key owner.json authorizer.json facilitator.json; do
  cp ~/.gyblos/seller/$key ~/gyblos-keys-backup/
done
```

On Windows, copy the same four files from `%USERPROFILE%\.gyblos\seller\`.

Move the copy to a USB drive or a password manager, then delete it from the computer.

<Callout type="error" title="owner.json controls your USDC">
  Anyone with `owner.json` can move the USDC on your owner address, and a
  transfer cannot be undone. The file uses the Solana CLI keypair format, so any
  Solana wallet can import it. Never upload it, paste it in a chat or send it to
  support.
</Callout>

### What a key backup is not [#what-a-backup-is-not]

- **Not a full restore.** Payment records, the public sequence and the registration state must match what is
  on chain and in the index. Never copy old files back over a running seller.
- **Not a desktop app backup.** A desktop app wallet backup belongs to another application and does not
  restore a seller.
- **Not a reset.** If keys, seller state or locks are missing or damaged, stop changing the data and ask
  Gyblos for help. Never delete a lock, a sequence file or a journal to make startup pass, and never clear
  the registration state to force a new attempt; see
  [Register and publish](/en/sellers/register-publish#complete-solana-enrollment-if-requested).

## Information you can send for support [#information-you-can-send-for-support]

These commands print public identifiers, codes and aggregate activity, without keys, tokens or buyer
messages:

```sh
cd ~/gyblos-seller
docker compose exec seller gyblos seller status
docker compose images seller
```

On a native seller, run `gyblos seller status` and `gyblos --version`. If the seller is not running, use
`gyblos doctor` and send the relevant code. Read the output before you share it, especially if your setup is
customized.

Never send `seller.env`, invite codes, environment dumps, `docker inspect` output, role files, receipts, raw
logs or screenshots of the registration prompt. Ask for help in the [Gyblos Telegram](https://t.me/gyblos).

## Verify your GitHub account [#verify-github]

You can show buyers which GitHub account runs your seller. This is optional. The index must already know
your seller: it must be registered, or currently publishing its models. `gyblos seller status --online`
shows `listed in the index` in its `discovery` line while the seller is publishing. The link has two parts: a
gist owned by your GitHub account with a file named `gyblos-proof.txt` that contains the line
`gyblos-node=NODEID`, and a claim signed by your node key that names the account and the gist. The
discovery index checks the signature when it receives the claim, and checks the gist itself, with no GitHub
token. Anyone can check the gist, but the index doesn't keep or publish the signed claim, so the public
view shows the index's result, not a signature others can check.

A verified account is a public label. It doesn't prove the quality of your answers or the code your seller
runs. Your GitHub account name and gist become public: see what is shared in
[Data and privacy](/en/reference/data-and-privacy#github). Every flag is in the
[CLI reference](/en/reference/cli#verify-github).

In the commands below, replace `USER` with your GitHub user name. For a Docker seller, run them from
`~/gyblos-seller` with `docker compose exec seller` in front, as shown.

### With the GitHub CLI [#verify-github-with-gh]

If the GitHub CLI (`gh`) is installed and signed in as `USER`, the command makes the gist for you:

1. Sign in to `gh` with the same account, if you haven't yet:

   ```sh
   gh auth login
   ```

2. Run:

   ```sh
   gyblos seller verify github USER
   ```

The command creates a public gist described `Gyblos node verification NODEID` with the file `gyblos-proof.txt`, signs
the claim and sends it to the index. If an earlier run was interrupted, it reuses the gist that run made.
When it works, it prints `Verified: GitHub account USER is linked to seller NODEID.` and the gist address.

If `gh` isn't installed, or is signed in as another account (the command says so), the command doesn't use it
and shows the steps below. The Docker image doesn't include `gh`, so a Docker seller follows the steps below.

### Without the GitHub CLI [#verify-github-by-hand]

1. Run the command:

   ```sh
   gyblos seller verify github USER
   ```

   For a Docker seller:

   ```sh
   cd ~/gyblos-seller
   docker compose exec seller gyblos seller verify github USER
   ```

2. It prints the text for the proof file. It looks like this, with your seller's NodeId:

   ```text
   This GitHub account runs the Gyblos seller below.
   gyblos-node=NODEID
   ```

3. Open [gist.github.com](https://gist.github.com) signed in as `USER`. Name the file exactly
   `gyblos-proof.txt`, paste the text and create the gist. A public or a secret gist both work; a secret
   gist's address still becomes public through the index.
4. Copy the gist's address from the browser and paste it when the command asks for `Gist URL`.

If the command can't ask, or you closed it, pass the address yourself:

```sh
gyblos seller verify github USER --gist GIST_URL
```

You can stop the command with Ctrl+C at any point and run it again: it saves its progress in the seller home
and skips what is done.

### What each state means [#github-states]

| State      | What it means                                                                                                                                                                                                                                               |
| ---------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `verified` | The last check GitHub answered found the proof line in your gist. Buyers see the account and the gist in the index's network list.                                                                                                                          |
| `pending`  | The index has your claim but hasn't found the proof yet. It isn't shown in the network list, but anyone can read it at `GET /v1/identity/github/<NodeId>`. The index checks again about every 6 hours, for up to 7 days; after that, run the command again. |
| `lost`     | The account was verified, but the last check didn't find the proof: the gist, the file or the line is gone, or the account was renamed. Buyers no longer see it.                                                                                            |

Only `verified` means the proof was found. When GitHub doesn't answer, the claim keeps its current state:
`pending` stays `pending` and `verified` stays `verified`. The check time shows the last attempt, even one
that failed.

### Good to know [#github-good-to-know]

- **The index checked moments ago.** The command prints `waiting N s to ask again (Ctrl+C is safe)` and asks
  once more by itself. It waits only once: if the wait is longer than 2 minutes, or the index answers the
  same after that wait, it stops and tells you to run it again later.
- **Change the account or the gist.** Run the command again with the new `USER`, or with `--gist` and the new
  gist. The claim goes back to `pending` until the index checks the new gist.
- **Keep the gist.** The index checks it again about every 6 hours. If you delete the gist, rename its file or
  remove the line, the state becomes `lost`.
- **Several sellers.** One GitHub account can verify several sellers, each with its own
  `gyblos-node=NODEID` line. With `gh`, the command makes one gist per seller. By hand, the simplest is one
  gist: add each seller's line, on its own line, to the same `gyblos-proof.txt` and pass that gist to each
  seller with `--gist`. Removing a line from the shared file affects only that seller. The index reads only the first 16 KiB
  of the file, about 200 lines: a line beyond that is ignored, so its seller is not found: `lost` if it was verified before, otherwise it stays `pending`.

### Check the state [#github-check]

```sh
gyblos seller verify github --status
gyblos seller status --online
```

`--status` shows the account, the gist address, the state, the reason, when the index last tried to check
and, while `verified`, since when. The last try can be one where GitHub didn't answer, so it isn't the last
time the proof was found.

`gyblos seller status --online` shows the account and state in its `github` line, and the gist address only
while `verified`. It asks the index only when publishing is on and the seller lists at least one model;
otherwise the line is missing, for example on a registered seller with publishing off: use
`gyblos seller verify github --status` instead. For a Docker seller, put `docker compose exec seller` in front of both.

### Remove it [#github-remove]

```sh
gyblos seller verify github --cancel
```

The index stops linking your seller to the account and the command removes its progress file. The gist
stays on GitHub: delete it yourself at [gist.github.com](https://gist.github.com) if you no longer want it.

### Common errors [#github-errors]

Each error starts with a sentence that says what to do and ends with a code in brackets.

| Code                                                     | What happened and what to do                                                                                                                                                    |
| -------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `VERIFY_PROOF_FILE_MISSING`                              | The gist exists but has no file named `gyblos-proof.txt`. Rename the file in the gist to exactly that name and run the command again.                                           |
| `VERIFY_PROOF_MISSING`                                   | The file doesn't contain `gyblos-node=NODEID` for this seller. Add the line on its own and run the command again.                                                               |
| `VERIFY_GIST_OWNER_MISMATCH`                             | The gist belongs to another GitHub account. Create the gist while signed in as `USER`.                                                                                          |
| `VERIFY_GIST_NOT_FOUND`                                  | GitHub has no such gist for `USER`: check the address and the user name. If the gist was deleted, run the command again to make a new one, or pass a new address with `--gist`. |
| `VERIFY_NOT_VERIFIED` with `could not reach GitHub`      | The index couldn't reach GitHub. Your claim keeps its current state. Run the command again in a few minutes.                                                                    |
| `VERIFY_NOT_VERIFIED` with `checked this seller moments` | The index checked your seller moments ago, and the wait is longer than 2 minutes or the index still said so after the one wait. Run the command again in a minute.              |
| `VERIFY_GH_FAILED`                                       | The GitHub CLI couldn't create the gist. Create it by hand and run the command with `--gist`.                                                                                   |
| `DISCOVERY_UNKNOWN_NODE`                                 | The index doesn't know your seller yet. [Register](/en/sellers/register-publish) it, or publish its models, first.                                                              |
| `DISCOVERY_STALE_CLAIM`                                  | The index holds a newer claim from this seller. The command already tried once more. Check this computer's clock, then run the command again.                                   |
| `DISCOVERY_RATE_LIMITED`                                 | The index got too many attempts. Wait a minute and run the command again.                                                                                                       |
| `VERIFY_ACCOUNT_INVALID`                                 | That is not a GitHub user name. Use letters, digits and single hyphens, at most 39 characters.                                                                                  |
| `VERIFY_GIST_INVALID`                                    | That is not a gist address or id. Copy the address of your gist from gist.github.com.                                                                                           |
| `VERIFY_NO_GIST`                                         | The command couldn't ask for the gist address, for example in a script. Create the gist, then run the command with `--gist`.                                                    |
| `VERIFY_SIGNING_FAILED`                                  | The node key couldn't sign the claim. Run `gyblos doctor`.                                                                                                                      |
| `VERIFY_STATE_FAILED`                                    | The command couldn't save its progress in the seller home. Check that the seller folder is yours and writable (`gyblos doctor`), then run the command again.                    |

## Privacy [#buyer-data-and-network-privacy]

A local engine processes buyers' messages on your machine; do not store or share them. A remote engine
provider also receives them. Encrypted transport and relays do not make your seller anonymous: relay
operators and network peers see connection metadata. Signed receipts do not prove which model answered or
that an answer is correct.

Release builds upload content-free receipts and telemetry observations to the Gyblos metrics collector. See
[what your seller sends](/en/sellers/operate#data-your-seller-sends) and
[Data and privacy](/en/reference/data-and-privacy).
