title: Identidad
description: Conserva el volumen del vendedor y distingue identificadores públicos de archivos privados.

Un vendedor tiene cuatro llaves privadas, creadas una sola vez por el instalador: la **llave del nodo** (su
NodeId público), el **dueño** (`owner`, registrado en 8004 y que recibe tus USDC), el **autorizador** y el
**pagador de comisiones**. Para qué sirve cada una está en [cobrar](/es/sellers/get-paid#llaves). Conserva la
identidad persistente creada al instalar. `seller init` escribe configuración; no crea ni recupera esas llaves.

## Almacenamiento [#dónde-se-guarda-cada-cosa]

| Ubicación en la instalación suministrada        | Uso                                                                                             | Regla para compartir                                                              |
| ----------------------------------------------- | ----------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------- |
| `~/gyblos-seller/config.toml`                   | Modelos, cuotas y publicación                                                                   | Revísalo antes de compartir; las URLs personalizadas pueden contener credenciales |
| `~/gyblos-seller/compose.yaml`                  | Contenedores y referencias a volúmenes                                                          | Consérvalo con la instalación; revisa valores personalizados antes de compartir   |
| `~/gyblos-seller/seller.env`                    | Credenciales de proveedores (claves de API), si una oferta las necesita                         | Privado; nunca lo subas ni lo muestres                                            |
| Volumen con nombre de Docker montado en `/data` | Llaves, estado del rol, intentos privados de registro, secuencia pública, recibos y tokenizador | Privado; nunca subas el volumen ni sus archivos                                   |
| Volumen separado de Ollama                      | Datos del modelo descargado                                                                     | Consérvalo para evitar descargas innecesarias                                     |

El proyecto de Compose determina los nombres de los volúmenes. Mover o renombrar la instalación puede
seleccionar otro proyecto y hacer que el vendedor parezca nuevo. No lo muevas, cambies el nombre del
proyecto ni purgues sus volúmenes para resolver un problema.

## Conserva la identidad [#conserva-la-identidad-al-detener]

Usa `docker compose stop seller` para dejar de servir. `docker compose down` conserva los volúmenes con nombre.
`docker compose down -v` los elimina y pierde las llaves del vendedor. Una invitación consumida está vinculada
al NodeId original y no registra una identidad recién generada.

## Respalda las llaves [#respalda-las-llaves]

Guarda una copia fuera de línea de los cuatro archivos de llaves, como mínimo `owner.json` (tus USDC y el
registro 8004) y `node.key` (el NodeId con el que usaste tu invitación). Cópialos una vez después de instalar;
nunca cambian. Con Docker, ejecuta esto desde `~/gyblos-seller`:

```bash
mkdir -p ~/gyblos-keys-backup && chmod 700 ~/gyblos-keys-backup
for key in node.key owner.json authorizer.json facilitator.json; do
  docker compose cp "seller:/data/seller/$key" ~/gyblos-keys-backup/
done
```

Sin Docker los mismos archivos están en `~/.gyblos/seller/` (cópialos con `cp`); en Windows están en `%USERPROFILE%\.gyblos\seller\`. Pasa la copia a un pendrive o a un gestor
de contraseñas y bórrala del computador. Quien tenga `owner.json` puede mover tus USDC; nunca lo subas, lo
pegues en un chat ni lo envíes a soporte. `owner.json` usa el formato de par de llaves de la CLI de Solana, así
que una billetera de Solana puede importarlo para llegar a tus fondos aunque no tengas el vendedor.

Una copia de las llaves **no** es una restauración completa. No copies archivos viejos encima de un vendedor
en marcha: los registros de pago, la secuencia pública y el estado del registro deben coincidir con lo que está
en la cadena y en el índice, y una copia vieja puede romperlos. La copia de la cartera de escritorio pertenece a
otra aplicación y no recupera este vendedor. Si faltan o están dañados las llaves, el estado del rol o los
bloqueos de secuencia, deja de modificar los datos y contacta con Gyblos. Nunca borres un bloqueo, archivo de
secuencia o journal solo para conseguir que arranque.

El volumen también guarda estado privado de registro, incluida una llave de asset y posiblemente
bytes de transacciones firmadas. Nunca compartas ese archivo ni borres su bloqueo para forzar un reintento.
Repetir el registro puede reenviar un intento ya aprobado; sigue [la guía de registro](/es/sellers/register-publish).

### Datos para soporte [#qué-puedes-enviar-para-pedir-ayuda]

```sh
cd ~/gyblos-seller
docker compose exec seller gyblos seller status
docker compose images seller
```

El comando de estado está diseñado para mostrar identificadores públicos, códigos y actividad agregada sin
llaves, tokens ni mensajes de compradores. Si el contenedor no está disponible, usa
`docker compose run --rm seller gyblos doctor` y envía el código relevante. Lee la salida antes de compartirla,
especialmente si personalizaste la instalación.

No envíes `seller.env`, códigos de invitación, volcados del entorno, `docker inspect`, archivos de rol, recibos,
logs completos ni capturas de la pregunta de registro. Pide ayuda en el [Telegram de Gyblos](https://t.me/gyblos).

## Privacidad [#datos-del-comprador-y-privacidad-de-red]

El motor local procesa los mensajes en tu equipo. No guardes ni compartas su contenido.
Un motor remoto también los recibe. El transporte cifrado y los relays no hacen anónimo al vendedor;
los operadores de relay y los participantes de red tienen su propia visibilidad. Firmar identidades y recibos
no verifica de forma independiente el modelo remoto ni la corrección de las respuestas.
