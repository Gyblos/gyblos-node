El comando `gyblos` ejecuta y administra un nodo vendedor. Esta página lista cada comando, sus opciones y
sus códigos de salida.

## Cómo ejecutar gyblos [#cómo-ejecutar-gyblos]

| Instalación                              | Ejecuta un comando así                                                   |
| ---------------------------------------- | ------------------------------------------------------------------------ |
| Vendedor Docker, contenedor en marcha    | `docker compose exec seller gyblos COMMAND`, desde `~/gyblos-seller`     |
| Vendedor Docker, contenedor detenido     | `docker compose run --rm seller gyblos COMMAND`, desde `~/gyblos-seller` |
| Vendedor nativo (macOS, Linux o Windows) | `gyblos COMMAND`                                                         |
| Código fuente                            | `pnpm gyblos COMMAND`, desde el repositorio                              |

Reemplaza `COMMAND` por un comando de la tabla siguiente. Los ejemplos de esta página usan la forma Docker.

## Comandos [#índice-de-comandos]

| Comando                           | Opciones                                                            | Códigos de salida                                            |
| --------------------------------- | ------------------------------------------------------------------- | ------------------------------------------------------------ |
| `gyblos start`                    | Ninguna                                                             | Corre hasta que lo detienes                                  |
| `gyblos setup`                    | `--role seller --mint MINT`                                         | 0 llaves listas; distinto de 0 si falla                      |
| `gyblos tokenizer`                | Ninguna                                                             | 0 verificado; distinto de 0 si falla                         |
| `gyblos --version`                | Ninguna                                                             | 0                                                            |
| `gyblos --help` / `gyblos -h`     | Ninguna                                                             | 0 imprime el uso en la salida estándar                       |
| `gyblos config validate`          | `--config PATH`                                                     | 0 válido; 1 inválido o error de uso                          |
| `gyblos doctor`                   | `--online`                                                          | 0 ninguna comprobación falló, aunque haya avisos; 1 un fallo |
| `gyblos seller status`            | `--online`                                                          | 0 solo con `RUNNING`; 1 con cualquier otro estado o error    |
| `gyblos seller register`          | Ninguna                                                             | 0 registrado o ya registrado; 1 fallo                        |
| `gyblos seller init`              | Consulta [`seller init`](#opciones-de-init-para-un-checkout-nativo) | 0 escrito; 1 fallo; 130 pregunta cancelada                   |
| `gyblos seller service install`   | `--memory SIZE`, `--cpu PERCENT`, `--dry-run`                       | 0 éxito; 1 fallo                                             |
| `gyblos seller service uninstall` | `--dry-run`                                                         | 0 éxito; 1 fallo                                             |
| `gyblos logs`                     | Consulta [`logs`](#logs-operativos-locales)                         | 0 lectura completa; 1 error de uso o datos ilegibles         |

No existe `gyblos stop`, ni flags generales `--home`, `--relay`, `--rpc-url` o `--discovery-url`. Detén un
vendedor Docker con Compose y un vendedor nativo mediante su servicio (consulta
[Operación](/es/sellers/operate)). Para otros ajustes usa las
[variables de entorno](/es/reference/configuration#variables-que-prevalecen-sobre-el-archivo).

### start [#start]

`gyblos start` ejecuta el nodo vendedor en primer plano con `GYBLOS_CONFIG`, o con `./config.toml`. La
imagen Docker y el servicio en segundo plano lo ejecutan por ti. No arranques un segundo vendedor sobre el
mismo home.

### setup y tokenizer [#setup-y-tokenizer]

`gyblos setup --role seller --mint MINT` crea las llaves de dueño, de nodo y de pago del vendedor e
imprime su rol público. Conserva las llaves que ya existen y añade las llaves de pago a un vendedor que no
las tiene. No contacta ningún RPC ni fondea nada. `gyblos tokenizer` descarga y verifica el tokenizador
público fijado e imprime `Pinned tokenizer verified.` El instalador ejecuta ambos por ti.

### --version [#version]

`gyblos --version` imprime la versión publicada. Desde el código fuente imprime `source`.

## Revisa la configuración [#valida-la-configuración-montada]

```sh
cd ~/gyblos-seller
docker compose run --rm seller gyblos config validate --config /config/config.toml
```

Si todo va bien imprime `OK`, la configuración efectiva y de dónde viene cada valor, las ofertas y los
nombres de las variables secretas con `set` o `not set`. Si falla imprime códigos de problema y rutas de
claves. Nunca imprime un valor tomado del entorno y muestra las URL solo como origen. Aun así, revisa la
salida antes de compartirla. `config validate` analiza el archivo y el entorno; no comprueba el motor ni
otras condiciones de arranque. `gyblos doctor` sí lo hace.

Cada comando elige su archivo de configuración de forma distinta:

| Comando                                | Archivo de configuración                                       |
| -------------------------------------- | -------------------------------------------------------------- |
| `config validate`                      | `--config PATH`, si no `./config.toml`; ignora `GYBLOS_CONFIG` |
| `start`, `doctor`, `seller init`       | `GYBLOS_CONFIG`, si no `./config.toml`                         |
| `seller status`, `register`, `service` | No aceptan `--config`                                          |

En el contenedor Docker, pasa `/config/config.toml` a `config validate` de forma explícita.

## Diagnostica el arranque [#diagnostica-el-inicio]

```sh
cd ~/gyblos-seller
docker compose run --rm seller gyblos doctor
```

Doctor imprime `OK`, `WARN` o `FAIL` en cada comprobación, con códigos y pistas, y luego los límites
efectivos del vendedor y su identidad pública. No arranca un vendedor, no genera respuestas ni escribe
estado. Solo prueba motores locales. `--online` además pide a los motores remotos su lista de modelos y
compara el reloj con el índice de descubrimiento; envía las credenciales del proveedor al proveedor
configurado. Que doctor pase no prueba que el modelo pueda generar. Si algo falla, consulta
[Solución de problemas](/es/help/troubleshooting).

## Estado y registro [#estado-y-registro]

```sh
cd ~/gyblos-seller
docker compose exec seller gyblos seller status
docker compose exec seller gyblos seller status --online
docker compose exec seller gyblos seller register
```

`seller status` solo lee. `--online` además busca el NodeId del vendedor en el índice de descubrimiento.
Mientras el índice rechace o falle la publicación de este vendedor, la línea de descubrimiento agrega
`publishing refused:` y un código estático. Mientras sirva algún modelo, una línea `uptime` muestra qué
tan seguido el índice aceptó la presencia de este vendedor en las últimas 24 horas, 7 días y 30 días, y
`online, last presence … ago` u `offline since …`; esa consulta envía al índice el NodeId, que es público. El
resumen de actividad sale de los recibos firmados guardados en el equipo; no es un saldo de cuota. La línea
`receipt queue` muestra los recibos que esperan subirse al recolector de métricas, los bytes reservados
para ellos y las escrituras rechazadas. `FULL` significa que no se pueden guardar recibos nuevos hasta que
se suban algunos. En una versión publicada, status también avisa cuando hay una versión más nueva (consulta
[Datos y privacidad](/es/reference/data-and-privacy#búsqueda-de-actualizaciones)).

`seller register` lee el código de invitación desde una terminal interactiva o desde `GYBLOS_INVITE`, nunca
desde un argumento de la línea de comandos. Pregunta antes de firmar y enviar un registro en devnet que
cuesta SOL, y no cambia `config.toml` ni publica. Lee [Registra y publica](/es/sellers/register-publish)
antes de ejecutarlo.

## seller init [#opciones-de-init-para-un-checkout-nativo]

`gyblos seller init` escribe un `config.toml` inicial con una oferta gratis en devnet. No instala Docker,
no crea llaves, no descarga modelos ni arranca un motor. El instalador escribe su propio `config.toml`, así
que `seller init` solo hace falta desde el código fuente o en una instalación hecha a mano. En el vendedor
Docker, edita el archivo del host: el contenedor monta la configuración en solo lectura.

| Flag                                 | Significado y valor por defecto                                                                                        |
| ------------------------------------ | ---------------------------------------------------------------------------------------------------------------------- |
| `--engine ollama\|openai\|anthropic` | Tipo de motor; por defecto `ollama`                                                                                    |
| `--url URL`                          | Por defecto Ollama `http://127.0.0.1:11435`; OpenAI `https://api.openai.com/v1`; Anthropic `https://api.anthropic.com` |
| `--model ID`                         | Por defecto `qwen3:0.6b` con Ollama; obligatorio, o se pregunta, con motores remotos                                   |
| `--upstream-model NAME`              | El nombre del modelo en el motor; por defecto, el modelo ofrecido                                                      |
| `--context-tokens N`                 | Obligatorio, o se pregunta, con OpenAI y Anthropic; omítelo con Ollama                                                 |
| `--api-key-env NAME`                 | Nombre de la variable de la API key; por defecto `OPENAI_API_KEY` o `ANTHROPIC_API_KEY`                                |
| `--api-key-env none`                 | Sin API key, solo para OpenAI                                                                                          |
| `--daily-cap N`                      | Por defecto `200000` tokens                                                                                            |
| `--per-buyer-cap N`                  | Por defecto `50000` tokens                                                                                             |
| `--publish` / `--no-publish`         | Publicación; desactivada por defecto; usa uno u otro                                                                   |
| `--force`                            | Reemplaza un archivo regular existente; nunca sigue un enlace simbólico                                                |

En una terminal pregunta lo que falta; un script recibe los flags y los valores por defecto. Sin `--force`
se niega a reemplazar un archivo existente. Comprueba la configuración con una credencial de relleno, así
que no prueba que tu API key funcione. Su puerto de Ollama por defecto, `11435`, es distinto del de los
instaladores, que usan `11434`.

## Servicio en segundo plano [#servicios-nativos-en-segundo-plano]

`gyblos seller service install` ejecuta un vendedor nativo en segundo plano con la cuenta que lo instala:
una unidad de usuario de systemd en Linux, un launch agent en macOS o una tarea programada al iniciar
sesión en Windows (solo la versión empaquetada). Ejecútalo con la cuenta del vendedor, nunca como root y
nunca dentro del contenedor Docker. El instalador lo ejecuta por ti.

- Antes de instalar, ejecuta `doctor` con el entorno propio del servicio y rechaza un vendedor que no
  podría arrancar.
- El servicio lee solo el `seller.env` del home (líneas estrictas `NAME=value`, permisos solo para el
  dueño), más las rutas del home y de la configuración guardadas al instalar. No hereda las variables de tu
  terminal.
- `--memory` vale `2048M` por defecto, que también es el mínimo. `--cpu` vale `100%` por defecto. Solo
  Linux aplica estos límites.
- `--dry-run` muestra lo que haría sin instalar.
- `uninstall` detiene el vendedor y quita el servicio. Conserva las llaves y la configuración.

## logs [#logs-operativos-locales]

```sh
gyblos logs --role buyer
gyblos logs --role buyer --follow --level error
gyblos logs --role buyer --json --component buyer-http --operation chat
```

`gyblos logs` lee el log de diagnóstico local, sin contenido, de un rol. Nunca arranca un nodo ni contacta
un servicio. El comprador local escribe este log; el nodo vendedor escribe su salida en el log de su
servicio (`docker compose logs seller`, `service.log` en el home o `journalctl --user -u gyblos-seller`).

| Opción                                                        | Significado                                                           |
| ------------------------------------------------------------- | --------------------------------------------------------------------- |
| `--role buyer\|seller`                                        | De qué rol leer; por defecto `seller`                                 |
| `--level debug\|info\|warn\|error`                            | Gravedad mínima                                                       |
| `--component NAME`, `--operation NAME`, `--correlation-id ID` | Filtros                                                               |
| `--limit N`                                                   | De 1 a 1000 registros; por defecto 100                                |
| `--follow`                                                    | Tras los últimos registros, sigue imprimiendo los nuevos hasta Ctrl+C |
| `--json`                                                      | Imprime los mismos registros como líneas JSON                         |

Si no hay log, el resultado es vacío, no un error. Los logs tienen tamaño acotado y se quedan en el equipo;
que falte un registro no prueba que nada falló. Si los datos son ilegibles o inseguros, sale con
`DIAGNOSTICS_UNAVAILABLE`.

## Comandos del instalador [#comandos-del-instalador]

Vuelve a ejecutar el instalador desde donde lo guardaste:

| Comando                   | Qué hace                                                                            |
| ------------------------- | ----------------------------------------------------------------------------------- |
| `sh install.sh`           | Instala o actualiza el vendedor; en una terminal luego ofrece registrar y publicar  |
| `sh install.sh publish`   | Lista el vendedor instalado en el índice de descubrimiento (después de registrarlo) |
| `sh install.sh unpublish` | Lo retira del índice; sigue funcionando                                             |
| `sh install.sh update`    | Descarga el instalador de la última versión, lo comprueba y lo ejecuta              |

En Windows, ejecuta los mismos subcomandos con
`powershell -ExecutionPolicy Bypass -File install.ps1 SUBCOMMAND`.

El instalador lee estas variables opcionales:

| Variable                     | Significado                                                                                               |
| ---------------------------- | --------------------------------------------------------------------------------------------------------- |
| `GYBLOS_MODE`                | `docker` o `native` (solo `install.sh`); por defecto, el de la instalación existente o Docker si funciona |
| `GYBLOS_DIR`                 | Solo `install.sh`: carpeta del vendedor Docker; por defecto `~/gyblos-seller`                             |
| `GYBLOS_HOME`                | Home del vendedor nativo; por defecto `~/.gyblos` (Windows: `%USERPROFILE%\.gyblos`)                      |
| `GYBLOS_IMAGE`               | Solo `install.sh`: imagen del vendedor; por defecto, la versión fijada en el instalador                   |
| `GYBLOS_RELAY_TOKEN`         | Solo para un relay que exige token                                                                        |
| `GYBLOS_REQUIRE_SIGNATURE=1` | Se detiene salvo que cosign verifique la firma de la versión                                              |
| `GYBLOS_GUIDED=0`            | Imprime los pasos para registrar y publicar en lugar de preguntar                                         |
| `GYBLOS_MODIFY_PATH=0`       | Solo `install.ps1`: no añade `gyblos` a tu `PATH` de usuario                                              |
| `GYBLOS_RELEASE_URL`         | Solo `install.ps1`: desde dónde descargar las versiones; el checksum se sigue aplicando                   |
